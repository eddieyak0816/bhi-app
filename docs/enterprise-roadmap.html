Critical Blockers

🚨
Must Fix Before Production

These issues pose security risks or could cause data loss in a production environment.

1. Missing Database Migrations

Critical

The supabase/migrations/ directory exists but contains no migration files. This means:

  • Database schema is not version controlled
  • Cannot reliably recreate the database
  • Risk of schema drift between environments
  • No rollback capability for schema changes

Recommended Fix:

# Generate migrations from existing database
supabase db diff --schema public -f initial_schema

# Or create migration files manually for each table:
# - users, resources, health_goals, resource_types
# - lab_markers, logic_rules, user_preferences

2. Row Level Security (RLS) Not Enforced

Critical

Without RLS policies, any authenticated user can potentially access or modify any data in the database.

Required RLS Policies:

-- Example: Users can only read their own data
CREATE POLICY "Users can read own profile"
  ON users FOR SELECT
  USING (auth.uid() = id);

-- Example: Only admins can modify resources
CREATE POLICY "Admins can manage resources"
  ON resources FOR ALL
  USING (
    EXISTS (
      SELECT 1 FROM users
      WHERE id = auth.uid()
      AND role IN ('admin', 'super_admin')
    )
  );

3. API Keys in Client Code

High

Supabase anon key is exposed in client-side code. While this is expected for Supabase, it emphasizes the need for proper RLS policies.

Mitigation:

  • Implement strict RLS policies (see above)
  • Use Edge Functions for sensitive operations
  • Consider API rate limiting

4. No Input Validation

High

Form inputs lack comprehensive validation. Risk of invalid data being stored.

Recommended Libraries:

  • zod - TypeScript-first schema validation
  • react-hook-form - Form handling with validation

Expert Recommendations

🏗️

Dr. Sarah Chen

Enterprise Software Architect • 20+ years experience • Former AWS Principal Architect

"The BHI app has a solid React foundation, but needs architectural improvements for enterprise scale. Here are my key recommendations:"

  • Implement a proper routing solution. The current hash-based routing works but limits SEO and deep linking capabilities. Migrate to React Router v6 with proper route guards.
  • Add a service layer abstraction. Currently, components directly call Supabase. Create a service layer (e.g., ResourceService, UserService) to decouple data fetching from UI components.
  • Implement proper state management. As the app grows, React Context will become unwieldy. Consider Zustand or TanStack Query for server state management.
  • Add Error Boundaries. A single unhandled error can crash the entire app. Implement error boundaries around major sections (navigation, content, modals).
  • Create a component library. Extract common UI patterns into a design system. This ensures consistency and speeds up development.
  • Add lazy loading for routes. Use React.lazy() and Suspense to code-split routes. This improves initial load time significantly.
🔐

Marcus Williams, CISSP

Chief Security Officer • Healthcare Security Specialist • HIPAA Compliance Expert

"Healthcare applications require the highest security standards. Given the sensitive nature of health data, here are critical security measures:"

  • HIPAA Compliance Framework. Even if not legally required for this use case, following HIPAA guidelines builds trust. Implement audit logging, access controls, and data encryption policies.
  • Row Level Security is non-negotiable. Every table must have RLS policies. A user should never be able to see another user's health data, period.
  • Implement Content Security Policy (CSP). Add strict CSP headers to prevent XSS attacks. This is especially important for a health app where data integrity is critical.
  • Add rate limiting. Protect authentication endpoints and API routes from brute force attacks. Supabase provides some protection, but add application-level limits too.
  • Implement audit logging. Track all data access and modifications. This is essential for compliance and security incident investigation.
  • Regular security assessments. Schedule quarterly penetration tests and code security reviews before each major release.
  • Data retention policies. Define how long user data is kept and implement automated deletion for inactive accounts.
🗄️

Dr. Raj Patel

Database Architect • PostgreSQL Core Contributor • Performance Optimization Expert

"PostgreSQL is an excellent choice via Supabase. Here's how to optimize for scale:"

  • Create proper indexes. Add indexes on frequently queried columns: resources.type, resources.tags (GIN index for array), user_preferences.user_id.
  • Implement database migrations. Use Supabase migrations or a tool like Prisma Migrate. Never modify production schema directly.
  • Add foreign key constraints. Ensure referential integrity between tables. This prevents orphaned records and maintains data consistency.
  • Implement soft deletes. Instead of DELETE, use deleted_at timestamps. This allows data recovery and maintains audit trails.
  • Partition large tables. As user data grows, partition tables like click_events by date for query performance.
  • Use materialized views for reports. Complex analytics queries should use materialized views refreshed periodically, not hit live tables.
  • Connection pooling. Ensure Supabase connection pooling is properly configured. Use PgBouncer settings for high-concurrency scenarios.

Technical Considerations

  • Storage costs: Video files are large. Consider implementing file size limits (e.g., 500MB)
  • Transcoding: Use a service like MUX or Cloudflare Stream for adaptive bitrate streaming
  • Thumbnails: Generate thumbnail previews automatically on upload
  • Progress tracking: Track video watch progress for engagement analytics
  • Captions: Support SRT/VTT caption uploads for accessibility

Recommended Architecture

Upload Flow:
1. User selects video file
2. Frontend chunks file and uploads to Supabase Storage
3. Trigger Edge Function on upload complete
4. Edge Function sends video to transcoding service
5. Transcoding service creates HLS playlist
6. Store playlist URL in resource_videos table
7. Frontend uses video.js or hls.js for playback

Implementation Approach

-- Materialized view for resource performance
CREATE MATERIALIZED VIEW mv_resource_performance AS
SELECT
  r.id,
  r.title,
  r.type,
  COUNT(DISTINCT ce.user_id) as unique_viewers,
  COUNT(ce.id) FILTER (WHERE ce.event_type = 'view') as views,
  COUNT(ce.id) FILTER (WHERE ce.event_type = 'click') as clicks,
  COUNT(ce.id) FILTER (WHERE ce.event_type = 'bookmark') as bookmarks,
  ROUND(
    COUNT(ce.id) FILTER (WHERE ce.event_type = 'click')::NUMERIC /
    NULLIF(COUNT(ce.id) FILTER (WHERE ce.event_type = 'view'), 0) * 100,
    2
  ) as click_through_rate
FROM resources r
LEFT JOIN click_events ce ON r.id = ce.resource_id
GROUP BY r.id, r.title, r.type;

-- Refresh daily via cron
SELECT cron.schedule('refresh-reports', '0 2 * * *',
  'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_resource_performance');

CREATE TABLE user_bookmarks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE,
  resource_id UUID REFERENCES resources(id) ON DELETE CASCADE,
  notes TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(user_id, resource_id)
);

CREATE TABLE user_resource_history (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID REFERENCES auth.users(id) ON DELETE CASCADE,
  resource_id UUID REFERENCES resources(id) ON DELETE CASCADE,
  last_viewed_at TIMESTAMPTZ DEFAULT NOW(),
  view_count INT DEFAULT 1,
  UNIQUE(user_id, resource_id)
);

-- Trigger to update history on view
CREATE OR REPLACE FUNCTION update_resource_history()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO user_resource_history (user_id, resource_id, last_viewed_at, view_count)
  VALUES (NEW.user_id, NEW.resource_id, NOW(), 1)
  ON CONFLICT (user_id, resource_id)
  DO UPDATE SET
    last_viewed_at = NOW(),
    view_count = user_resource_history.view_count + 1;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

Privacy Controls

  • Users can clear their history
  • Option to disable history tracking
  • Data export functionality (GDPR compliance)
  • Account deletion removes all history

-- Resource links: Anyone can read, admins can write
CREATE POLICY "Anyone can read resource links"
  ON resource_links FOR SELECT USING (true);
CREATE POLICY "Admins can manage resource links"
  ON resource_links FOR ALL USING (
    EXISTS (SELECT 1 FROM users WHERE id = auth.uid() AND role IN ('admin', 'super_admin'))
  );

-- Click events: Users can insert own events, admins can read all
CREATE POLICY "Users can insert own click events"
  ON click_events FOR INSERT WITH CHECK (auth.uid() = user_id OR user_id IS NULL);
CREATE POLICY "Admins can read all click events"
  ON click_events FOR SELECT USING (
    EXISTS (SELECT 1 FROM users WHERE id = auth.uid() AND role IN ('admin', 'super_admin'))
  );

-- User bookmarks: Users can only access their own
CREATE POLICY "Users manage own bookmarks"
  ON user_bookmarks FOR ALL USING (auth.uid() = user_id);

-- User history: Users can only access their own
CREATE POLICY "Users access own history"
  ON user_resource_history FOR ALL USING (auth.uid() = user_id);

-- 8. Materialized view for reports
CREATE MATERIALIZED VIEW mv_resource_performance AS
SELECT
  r.id,
  r.title,
  r.type,
  COUNT(DISTINCT ce.user_id) as unique_viewers,
  COUNT(ce.id) FILTER (WHERE ce.event_type = 'view') as views,
  COUNT(ce.id) FILTER (WHERE ce.event_type = 'click') as clicks,
  COUNT(ce.id) FILTER (WHERE ce.event_type = 'bookmark') as bookmarks
FROM resources r
LEFT JOIN click_events ce ON r.id = ce.resource_id
WHERE ce.created_at > NOW() - INTERVAL '30 days'
GROUP BY r.id, r.title, r.type;

CREATE UNIQUE INDEX idx_mv_resource_perf ON mv_resource_performance(id);
